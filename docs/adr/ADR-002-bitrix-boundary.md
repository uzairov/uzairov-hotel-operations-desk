# ADR-002: Граница между Operations Desk и Битрикс24

- Статус: принято
- Дата: 2026-08-20

## Решение

Housekeeping и техническое обслуживание живут только в Hotel Operations Desk.
Все остальные задачи сотрудников отеля остаются в Битрикс24. На этапе F0
интеграции между системами нет: ни синхронизации, ни вызовов API Битрикса, ни
дублирования задач.

## Контекст

Операционные задачи отеля ведутся в Битрикс24 — это источник истины по ТЗ
Hospitality OS. Появление второй системы означает, что у горничной возникает
второе место, где ей ставят задачи. Без явной границы персонал начнёт
выборочно пользоваться то одной, то другой, и данные разойдутся в первую же
неделю пилота.

Синхронизация выглядит очевидным решением, но это внешняя зависимость: чужие
права доступа, чужой владелец вебхука, задержки и молчаливые сбои. Опыт БПМ
показал, что отладка обмена с порталом занимает больше времени, чем сама
функциональность.

## Альтернативы

1. Двусторонняя синхронизация. Отклонено: нарушает условие F0 о независимости
   от внешних API, а стоимость отладки не оправдана до подтверждения, что
   продукт вообще приживётся.
2. Оставить housekeeping в Битриксе, в Operations Desk вести только статусы
   номеров. Отклонено: цикл «выезд → уборка → проверка → номер готов» рвётся
   между двумя системами, и главный сценарий продукта перестаёт быть цельным.

## Компромиссы

Часть сотрудников будет работать в двух интерфейсах. Это принимается осознанно
на время F0 и компенсируется тем, что граница проходит по типу работы, а не по
людям: у горничной весь её труд в одной системе.

## Последствия

- Граница объявляется персоналу до начала пилота, устно и письменно.
- Вопрос интеграции возвращается только после выхода из F0 и оформляется
  новым ADR.
- Задача, которая тянет за собой обращение к API Битрикса, на F0
  останавливается и выносится человеку.
