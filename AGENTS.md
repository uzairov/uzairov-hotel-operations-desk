# AGENTS.md — Hotel Operations Desk

## Статус документа

v0. Написан до первого коммита, то есть это гипотеза о том, что агенту нужно
знать. Правится по мере накопления `FACTORY-LOG.md`.

Правило правки: то, что пришлось объяснить агенту один раз — строчка в
FACTORY-LOG. Дважды — пометка WATCH. Трижды — переносится сюда.

---

## 1. Продукт

Hotel Operations Desk — приложение для персонала небольшого отеля: состояние
номеров, уборки, технические неисправности, операционные задачи.

Пользователи: администратор, управляющий, ресепшн, горничные и техники.
Первый деплой — собственный отель в Бухаре. Это реальный production с первой
недели, а не демо: любая ошибка видна персоналу в тот же день.

Продукт одновременно является первым клиентом AI Product Factory (этап F0).

## 2. Языки

Интерфейс — русский. Пользователи пишут по-русски, по-узбекски (латиница и
кириллица) и смешанно, с опечатками и сокращениями. Любая обработка
пользовательского текста обязана это учитывать.

Комментарии в коде и сообщения коммитов — русский или английский, но без
разнобоя внутри одного файла.

## 3. Стек

- Next.js + TypeScript, App Router
- API — Route Handlers и Server Actions, отдельного бэкенда нет
- Supabase: PostgreSQL, Auth, Storage
- Фон и расписание — Supabase Edge Functions и pg_cron
- AI — OpenAI, вызовы только через `lib/ai/provider.ts`
- Деплой — Vercel; CI — GitHub Actions
- Тесты — Playwright (e2e), Vitest (unit)
- Ошибки — Sentry

Второго рантайма в проекте нет и не появляется без ADR.

## 5. Как запустить и как проверить

```
pnpm install
pnpm dev            локальный запуск
pnpm lint
pnpm typecheck
pnpm test           unit
pnpm test:e2e       Playwright против preview или локального стенда
```

Перед PR обязаны проходить `lint`, `typecheck`, `test`, `build`.

## 6. Окружения

Два отдельных проекта Supabase: **staging** и **production**. У них разные
база, auth, storage и секреты. Общей базы нет ни при каких обстоятельствах.

- Preview на Vercel всегда смотрит в staging.
- В production попадает только то, что влито в `main`.
- Прямой пуш в `main` запрещён на уровне GitHub, всё через PR.

## 7. Архитектурные правила

1. Права проверяются **на сервере**: в RLS и в route handler. Проверка в UI —
   удобство, а не защита. PR, где доступ ограничен только скрытой кнопкой,
   отклоняется.
2. Роли: `admin`, `manager`, `reception`, `staff` (горничные и техники).
   Роль хранится в базе, не в токене клиента и не в localStorage.
3. Состояния номера: `clean`, `dirty`, `cleaning`, `inspected`, `out_of_order`,
   `maintenance`. Переходы описаны в одном модуле; свободная запись статуса
   мимо него запрещена.
4. Каждое изменение состояния номера или задачи пишет запись в `audit_log`.
   `audit_log` только дополняется: `UPDATE` и `DELETE` по нему запрещены.
5. `trace_id` создаётся на входе пользовательского действия и проходит через
   API, вызов модели, мутацию базы и запись аудита. Новая мутация без
   проброса `trace_id` не принимается.
6. Обращения к OpenAI — только через `lib/ai/provider.ts`. Продуктовый код
   импортирует `AIService`, а не SDK провайдера.

## 8. Что нельзя менять никогда

- Схему и содержимое `audit_log` задним числом.
- Правила доступа без явной задачи и без пометки риска «высокий».
- Прямые записи в production-базу мимо миграций.
- Секреты в коде. Только переменные окружения.
- Границу с Битрикс24 (см. `docs/adr/ADR-002`): housekeeping и техника живут
  здесь, всё остальное — в Битриксе. Никакой синхронизации на F0.
- AGENTS.md не редактируется инструментами. В Next.js это отключается
  параметром agentRules: false в next.config.ts — не удалять.

## 9. Что не входит в продукт

PMS, движок бронирования, OTA и channel manager, биллинг и платежи, фолио,
бухгалтерия, CRM, лояльность, гостевое приложение, замки, IoT, энергоучёт,
сложная аналитика.

Если задача тянет за собой что-то из этого списка — это сигнал остановиться и
спросить человека, а не расширять скоуп.

## 10. Миграции

- Миграции только вперёд, лежат в `supabase/migrations/`, именуются по времени.
- Каждая миграция **идемпотентна**: `if not exists`, `create or replace`,
  повторный прогон не должен падать.
- Применяет миграции CI, а не человек руками и не агент напрямую в базу.
- Порядок: сначала staging, зелёный прогон, потом production.
- Разрушающая миграция (удаление колонки, таблицы, изменение типа с потерей
  данных) требует отдельного approval человека, плана отката и дампа до
  применения. Агент такую миграцию предлагает, но не применяет.

## 11. API

- Route handlers в `app/api/`, один ресурс — один каталог.
- Валидация входа обязательна на сервере, схемой, а не вручную.
- Ответ об ошибке не раскрывает внутренние детали: ни SQL, ни стек, ни имена
  таблиц.
- Любой хендлер, меняющий данные, обязан: проверить роль, записать аудит,
  пробросить `trace_id`.

## 12. AI-функции

Главное правило F0:

**AI не создаёт операционные сущности самостоятельно.** Модель разбирает
сообщение и возвращает черновик, человек подтверждает или правит, и только
подтверждение создаёт задачу.

Каждое обращение к ассистенту логируется в `assistant_interactions`:
входной текст, черновик модели, итоговый подтверждённый результат, признаки
`accepted_without_edit` / `edited` / `discarded`, модель, версия промпта,
`trace_id`, время.

Промпты версионируются вместе с кодом. Изменение промпта — такой же PR, как
изменение кода, и требует прогона evals.

Датасет: `evals/operations-assistant/`. В нём обязаны быть примеры на русском,
узбекском (латиница и кириллица), в смешанной форме, с опечатками,
сокращениями и неформальными ссылками на номер. Стерильных формулировок в
датасете быть не должно — реальные пользователи так не пишут.

## 13. Конвенции кода

- TypeScript strict. `any` — только с комментарием, объясняющим почему.
- Серверная и клиентская логика не смешиваются в одном модуле.
- Доступ к базе — через `lib/db`, не разбросан по компонентам.
- Имена таблиц и колонок — `snake_case`, типы и компоненты — `PascalCase`.
- Файл больше ~300 строк — повод разделить, а не продолжать.

## 14. Канонические документы

- `docs/product/` — что и для кого строим.
- `docs/adr/` — принятые решения. **Агент обязан прочитать ADR до изменения
  архитектуры.** Решение, противоречащее ADR, требует нового ADR, а не
  молчаливого обхода.
- `docs/specs/` — технические спеки задач.
- Этот файл — правила работы с репозиторием.

Если код расходится с этими документами — расхождение фиксируется в PR, а не
решается в пользу кода по умолчанию.

## 15. Что обязано быть в PR

- [ ] Ссылка на задачу Linear, ветка создана по её имени.
- [ ] CI зелёный: lint, typecheck, test, build.
- [ ] Каждый критерий приёмки из задачи закрыт тестом, тест назван в описании.
- [ ] Миграция идемпотентна, план отката описан.
- [ ] Изменения не выходят за границы, объявленные в спеке (блок «не трогать»).
- [ ] Новые мутации пробрасывают `trace_id` и пишут аудит.
- [ ] Права проверены на сервере, а не только в UI.
- [ ] Если в ходе работы возникло трение — строчка в `FACTORY-LOG.md`, в этом
      же PR.

## 16. FACTORY-LOG.md

Отдельный файл в корне. В него дописывается всё, что мешало работе:

```
## 2026-08-2X — PR #NN

- Пришлось объяснить агенту порядок применения миграций → кандидат в AGENTS.md
- Второй раз вручную переносим задачу в In review после открытия PR → WATCH
- Третий раз Playwright неверно создаёт тестового пользователя → STANDARDIZE
```

Пометки: один раз — LOG, два — WATCH, три — STANDARDIZE или AUTOMATE.

Этот файл — единственный источник будущей фабрики. Заполняется по ходу, не по
памяти в конце.
